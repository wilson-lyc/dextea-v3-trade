# 接口文档规范（Example）

> 本文件是接口文档的**格式规范模板**。新增或修改接口文档时，必须遵循本文件的章节结构与写法。
> 实际接口文档见 [README.md](./README.md) 索引。

## 文件组织

- 一个接口一个 md 文件，存放于 `docs/api/` 目录。
- 文件名使用小写中划线命名，格式为 `{端}-{资源}-{动作}.md`，例如 `customer-create-order.md`、`store-mark-order-ready.md`。
- 新增接口后必须在 [README.md](./README.md) 索引中登记。

## 文档结构

每个接口文档必须且只能包含以下章节（按顺序）：

1. 接口名称（一级标题）
2. 接口说明
3. 请求地址
4. 请求头
5. 请求参数
6. 请求示例
7. 响应格式
8. 响应示例
9. 错误码字典

---

## 1. 接口名称

一级标题 `#`，使用中文动宾短语，如「创建订单」「标记订单制作完成」。与代码中接口的实际语义保持一致。

## 2. 接口说明

一段话说明接口用途、调用时机与特殊行为（如幂等、状态流转、副作用）。有前置条件或调用顺序要求的必须写明。

## 3. 请求地址

列出 HTTP 方法与完整路径，格式：

```
POST /api/v1/customer/orders
```

路径中包含动态参数时用 `{}` 占位并说明，如 `GET /api/v1/customer/orders/{orderId}`。

## 4. 请求头

用表格列出本接口必需的请求头。`Authorization` 与身份头（`X-Customer-Id` / `X-Store-Id`）为全站公共请求头，各文档仍需完整列出，方便单独阅读。

| 请求头 | 必填 | 说明 |
| ------ | ---- | ---- |
| Authorization | 是 | API 访问令牌，格式 `Bearer {token}` |
| X-Customer-Id | 是 | 顾客 ID，标识当前登录顾客 |

## 5. 请求参数

按「路径参数 / 查询参数 / Body 参数」分小节；某类参数不存在时省略该小节。每个参数用表格描述：

| 参数 | 类型 | 必填 | 说明 |
| ---- | ---- | ---- | ---- |

写法约定：

- **类型**：使用 `string` / `integer` / `long` / `decimal` / `boolean` / `object` / `array`。
- **必填**：`是` / `否`。选填参数要说明缺省时的行为。
- **说明**：写清业务含义、取值范围与格式约束（长度、精度、枚举值）。枚举值必须逐一列出 `值 - 含义`，与代码中枚举定义一致。
- **嵌套对象/数组元素**：在下方单独用表格描述，字段名带父级前缀（如 `items[].skuId`），或用「`items` 数组元素」小节。
- 请求 Body 与响应同构的字段（如订单项中由服务端填充的字段），必须注明「响应填充，请求无需传」。

## 6. 请求示例

给出可直接使用的 `curl` 示例（含请求头、路径参数、Body），Body 使用真实结构的 JSON。示例值应贴近真实业务，不使用 `xxx`、`foo` 等占位串。

## 7. 响应格式

- 先说明统一响应信封（见下），再列出 `data` 的字段表格，写法与请求参数一致。
- HTTP 状态码由错误码段决定（见下），成功时统一为 `200`。

**统一响应信封**（所有接口一致，不再在每篇文档中重复）：

```json
{
  "code": 0,
  "message": "成功",
  "data": { }
}
```

| 字段 | 类型 | 说明 |
| ---- | ---- | ---- |
| code | integer | 业务状态码，`0` 表示成功，非 `0` 见错误码字典 |
| message | string | 提示信息 |
| data | object \| null | 业务数据，失败时为 `null`（除特别说明外） |

## 8. 响应示例

给出成功响应的完整 JSON（含信封）。若同一接口存在多种业务形态的 `data`（如订单项分可用/不可用），分别给出示例。

## 9. 错误码字典

用表格列出**本接口可能返回**的全部业务错误码，是错误处理的唯一依据。按错误码升序排列：

| 错误码 | HTTP 状态码 | 说明 |
| ------ | ----------- | ---- |

写法约定：

- **只列本接口可能出现的错误码**，不罗列无关码。不确定时以代码中 `BizError` / `SystemException` 实际抛出的为准。
- **HTTP 状态码**由错误码统一推导，不需要逐接口另行约定：`4` 开头取错误码前 3 位（`40002→400`、`40100→401`、`40400→404`、`40901→409`、`42901→429`）；`2` 开头 → 400；`3` / `5` 开头 → 500。完整分段规范见 [error-codes.md](./error-codes.md)。
- 全站通用错误码（见下表）在每个接口的字典中都要包含其中与本接口相关者（至少：鉴权 40100、缺少请求头 40001、参数校验 40002）。
- 错误码新增或调整后，同步更新 [error-codes.md](./error-codes.md) 的全站错误码总表与相关接口文档。

### 全站通用错误码（摘自 `GlobalExceptionHandler` 与鉴权拦截器）

| 错误码 | HTTP 状态码 | 说明 |
| ------ | ----------- | ---- |
| 50000 | 500 | 系统繁忙，请稍后重试 |
| 50101 | 500 | 数据库访问异常（系统繁忙，请稍后重试） |
| 40001 | 400 | 缺少请求头（message 中带具体请求头名） |
| 40002 | 400 | 参数缺失 / 参数校验失败 / 请求体格式错误 / 参数类型不正确 |
| 40100 | 401 | 未登录（未携带令牌或令牌校验失败） |

## 完整示例

```markdown
# 创建订单

## 接口说明

顾客提交订单并创建支付交易。通过 `idempotencyKey` 保证幂等：同一 key 重复提交时返回 21014 错误，不会重复建单。

## 请求地址

POST /api/v1/customer/orders

## 请求头

| 请求头 | 必填 | 说明 |
| ------ | ---- | ---- |
| Authorization | 是 | API 访问令牌，格式 `Bearer {token}` |
| X-Customer-Id | 是 | 顾客 ID，标识当前登录顾客 |

## 请求参数

### Body 参数

| 参数 | 类型 | 必填 | 说明 |
| ---- | ---- | ---- | ---- |
| storeId | long | 是 | 门店 ID |
| diningMethod | integer | 是 | 用餐方式：`1` - 堂食，`2` - 外带 |
| paymentMethod | integer | 是 | 支付方式：`0` - 现金，`1` - 支付宝，`2` - 微信 |
| idempotencyKey | string | 是 | 幂等键，客户端生成，最长 64 字符 |
| items | array | 是 | 订单明细列表，见下方「items 数组元素」 |

### items 数组元素

| 参数 | 类型 | 必填 | 说明 |
| ---- | ---- | ---- | ---- |
| skuId | string | 是 | 商品 SKU 编码 |
| quantity | integer | 是 | 购买数量，必须大于 0 |

## 请求示例

（curl 示例）

## 响应格式

`data` 字段：

| 参数 | 类型 | 说明 |
| ---- | ---- | ---- |
| id | long | 订单 ID |
| orderNo | string | 订单号 |
| totalPrice | decimal | 订单总价（元） |

## 响应示例

（成功响应 JSON）

## 错误码字典

| 错误码 | HTTP 状态码 | 说明 |
| ------ | ----------- | ---- |
| 40001 | 400 | 缺少请求头 |
| 40002 | 400 | 参数缺失或校验失败 |
| 40100 | 401 | 未登录 |
```
