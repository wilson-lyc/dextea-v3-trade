# 制单 MQ 设计说明

本文档面向制单 MQ 的消费端团队，说明制单状态消息（Order Making MQ）的业务语义、触发条件、消息格式与生命周期，便于消费端正确对接与处理。**本文档不涉及代码实现细节**，仅从逻辑/应用层面描述。

---

## 1. 概述

制单 MQ 用于通知下游系统（如厨显、门店终端、第三方制单系统）**订单制作状态发生的关键变化**。下游可据此驱动出餐屏、打印小票、推送取餐提醒等动作。

- **消息中间件**：RocketMQ
- **Topic（默认）**：`order_making_status`（可通过配置 `ORDER_MAKING_MQ_TOPIC` 覆盖）
- **角色**：本服务**仅作为生产者**投递消息，不消费本 Topic。消费组由消费端团队自行定义，不在此配置。
- **是否启用**：由配置项 `ORDER_MAKING_MQ_ENABLED` 控制，默认 **关闭**。该开关同时控制生产者初始化与消息发送，只有开启后才会向 Topic 投递消息。

> 注意：本 Topic 仅承载"制作状态"维度的变化。订单的支付状态、取消、超时等变化不属于本 MQ 范畴（例如取消/支付超时虽会变更制作状态为"已取消"，但**不会**向本 Topic 发消息）。

---

## 2. 何时会发送消息（触发条件）

生产端**不是**在每一次制作状态写库时都发消息，而是仅针对以下两个业务节点，并且仅当状态确实发生了对应变更时才发送：

| 业务节点 | 触发动作 | 消息状态流转（from → to） | 发送条件 |
| --- | --- | --- | --- |
| 订单支付成功 | 系统将订单标记为已支付并进入制作中 | `PENDING` → `PREPARING` | 且仅当变更前状态确为 `PENDING`（支付成功前已处于待制作） |
| 订单制作完成 | 门店端标记订单制作完成 | `PREPARING` → `READY` | 且仅当变更前状态确为 `PREPARING`（制作中→制作完成） |

补充说明：

- **支付成功节点的语义**：一笔订单支付成功后，制作状态从"待制作"变为"制作中"，此时下游需要开始备餐/出单，因此发送消息。
- **制作完成节点的语义**：门店标记制作完成后，制作状态从"制作中"变为"制作完成"，下游可通知顾客取餐，因此发送消息。
- **已取餐（`READY` → `COLLECTED`）不发送本 MQ 消息**：门店标记已取餐后，系统不会向本 Topic 发送消息。
- **取消/支付超时（`→ CANCELLED`）不发送本 MQ 消息**：即使制作状态被置为"已取消"，系统也不会向本 Topic 发送消息，相关取消逻辑请消费端通过其他渠道（如支付回调 MQ、订单超时 MQ 或订单状态查询）获取。

### 发送时机（与数据库事务的关系）

消息的发送被安排在**订单数据落库的事务成功提交之后**进行，而不是在事务执行过程中。即：只有订单状态变更已成功持久化，才会对外投递消息。

这样做保证了：消费端收到消息时，对应订单的状态变更在订单库中已经可见，避免出现"消息到了但查不到状态"的不一致情况。

若生产端未启用（总开关或生产者开关关闭），则直接跳过发送，不会抛错，也不会有消息进入 Topic。

## 3. 消息格式

### 3.1 消息头部（RocketMQ 维度）

| 字段 | 取值说明 |
| --- | --- |
| Topic | `order_making_status`（或配置指定的 topic） |
| Tag | 状态流转标识，格式为 `<fromStatus>To<toStatus>`，取值为数字 code，例如 `0To1`、`1To2` |
| Keys | 订单数据库自增主键 `orderId`（用于去重、排查与轨迹追踪） |
| Body | JSON 字符串，见下方消息体 |

### 3.2 消息体（Body）字段

消息体为 JSON，包含以下字段：

| 字段名 | 类型 | 含义 |
| --- | --- | --- |
| `orderId` | Long | 订单数据库自增主键，作为消息 Keys，也是消费端关联订单的核心标识 |
| `storeId` | Long | 门店 ID，便于消费端快速识别消息所属门店并按门店过滤/路由 |
| `fromStatus` | int | 变更前制作状态的数字 code，取值见第 4 节枚举 |
| `toStatus` | int | 变更后制作状态的数字 code，取值见第 4 节枚举 |

> 说明：本系统与各下游团队共享同一份制作状态枚举字典，因此消息中直接传递枚举的**数字 code**，消费端按字典映射即可，无需在消息里携带字符串 name。

#### 示例

支付成功（进入制作中）：

```json
{
  "orderId": 123456,
  "storeId": 88,
  "fromStatus": 0,
  "toStatus": 1
}
```

制作完成：

```json
{
  "orderId": 123456,
  "storeId": 88,
  "fromStatus": 1,
  "toStatus": 2
}
```

对应消息 Tag 分别为 `0To1` 与 `1To2`。

---

## 4. 制作状态枚举

`fromStatus` / `toStatus` 取值为以下枚举的**数字 code**（系统间共享字典，消费端据此映射）：

| name | code | 中文含义 |
| --- | --- | --- |
| `PENDING` | 0 | 待制作 |
| `PREPARING` | 1 | 制作中 |
| `READY` | 2 | 制作完成 |
| `COLLECTED` | 3 | 已取餐 |
| `CANCELLED` | 4 | 已取消 |

> 本 MQ 只会推送 `0→1` 与 `1→2` 两种流转；`COLLECTED`(3)、`CANCELLED`(4) 为终态，但**不**经由本 MQ 推送。

---

## 5. 消息是否会过期（生命周期）

- **消息本身未设置过期时间 / 延迟投递**：生产端发送的是普通消息，没有为单条消息设置 TTL 或定时/延迟投递。消息一旦发送即进入 Topic 等待消费。
- **不保证实时性但保证可达**：消息在订单事务提交后发出，正常网络情况下近实时到达；若下游暂时不可用，RocketMQ 服务端会按自身默认保留策略暂存，待消费端恢复后继续投递。
- **消费端幂等建议**：消息以 `orderId` 作为 Keys，且 Tag 精确表达了本次状态流转（数字形式 `0To1`、`1To2`）。由于生产端在同一状态变更上可能因重试/并发出现重复投递，建议消费端以 `(orderId, fromStatus, toStatus)` 或 `(orderId, 事件顺序)` 做幂等处理，避免因重复消费产生重复出单等问题。
- **状态终态提示**：`COLLECTED`、`CANCELLED` 为制作状态的终态。本 MQ 不会主动推送这两个终态，但若消费端通过其他渠道获知订单进入终态，应注意不要因为缺少本 MQ 消息而遗漏处理。

---

## 6. 消费端对接建议（小结）

1. 订阅 Topic `order_making_status`（或对接方实际部署配置的值），消费组自行定义。
2. 用 Tag 过滤只关心的变化（`0To1` 开始制作、`1To2` 制作完成），或订阅全部 Tag。
3. 以 `orderId` 作为业务主键，结合 `fromStatus`/`toStatus` 做幂等。
4. 不要依赖本 MQ 获取"已取餐""已取消"等终态，这类信息请通过订单查询接口或对应其他 MQ 获取。
5. 收到消息后建议再次核对订单当前制作状态（以订单服务为准），因为极端并发下订单状态可能已进一步流转。
